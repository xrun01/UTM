# 国际化

UTM 用 String Catalog（`.xcstrings`）管理全部语言。英文是源语言，键就是英文原文。脚本在 `scripts/i18n/`，用 bun 运行。

## 文件

| 位置 | 内容 |
|---|---|
| `Platform/Localizable.xcstrings` | app 文案 |
| `Platform/macOS/InfoPlist.xcstrings` | 麦克风权限提示和文档类型名 |
| `Platform/macOS/Display/VMDisplayWindow.xcstrings` | xib 文案，键是 IB 对象 ID |
| `i18n/languages.json` | 语言清单，以及 Apple 代码和翻译接口代码的映射 |
| `i18n/check-exceptions.json` | 检查规则的例外，每条必须写明原因 |
| `i18n/removed.json` | 被删除的键的英文和译文，供审校参考 |
| `scripts/i18n/` | `sync.js`、`check.js`、公共库和单元测试 |

`vm/script/lib/sdkBuild.js` 负责 2 件事：构建时把提取结果写进 `build/i18n/`；把 3 个 catalog 编译进 `UTM.app/Contents/Resources/<lang>.lproj/`。

## 条目状态

| 状态 | 含义 | 是否编译进 app |
|---|---|---|
| 缺译 | 这种语言没有译文 | 运行时显示英文 |
| `needs_review` | 机翻，或英文改过后待复核 | 是 |
| `translated` | 人工译文，或已审校 | 是 |
| `stale` | 源码已经不用这个键 | 不允许提交，`sync.js` 会删除 |

## 新增或修改文案

构建脚本在 vm 仓库中，并按「vm 的上级目录 / UTM」找到 UTM。所以 vm 必须放在 UTM 旁边，构建命令在 2 个仓库的上级目录运行。其他命令在 UTM 仓库根目录运行。第 1 次运行脚本前，在 `scripts/i18n/` 中运行 `bun install`。

1. 在 Swift 代码中写英文文案。
2. 在 UTM 和 vm 的上级目录运行 `bun vm/script/buildApp.js`。
   结果：`UTM/build/i18n/` 中有最新的提取结果。
3. 在 UTM 根目录运行 `bun scripts/i18n/sync.js`。
   结果：新文案进入 catalog，源码已不用的键被删除。
4. 运行 `bun scripts/i18n/check.js --ci`。
   结果：输出 `0 个错误`。`--ci` 和 CI 的检查一致，能发现 catalog 中多出的键。
5. 提交源码、3 个 catalog，以及 `i18n/removed.json`（sync 写了它时会提示）。CI 不检查 `removed.json`，漏提交就会丢失被删除键的译文记录。

注意：如果 `xcode-select` 指向 Command Line Tools，构建前必须设置 `DEVELOPER_DIR`，例如 `export DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer`。Command Line Tools 没有 `ibtool` 和 `actool`。

sync 改的是 catalog，app 里的译文要重新构建后才更新。想在 app 里看到新译文时，再运行 1 次第 2 步。

`sync.js` 遇到下面 3 种构建输出时报错，不修改任何文件。这时重新运行第 2 步。理由：用不完整或过期的提取结果同步，会把正常的键当成无用的键删除。

- 源文件在构建开始后被修改，或者新增、删除了源文件。切换分支、`git pull`、格式化工具即使只改了修改时间，也算修改。
- 构建输出来自另一个目录（`--build-dir` 指向别的 checkout）。
- 构建清单缺少 `root` 或 `started_at`，说明 vm 的构建脚本版本过旧。

`sync.js` 先算完 3 张表，再先写 `i18n/removed.json`、后写 catalog。计算阶段出错时，任何文件都不变。每个文件单独原子写入，不会出现截断的文件。

## 机翻：`translate.js`

`translate.js` 调用 webc 翻译接口，补齐缺译条目。写入的译文状态是 `needs_review`，已有译文一律不动。

```bash
bun scripts/i18n/translate.js --dry-run         # 只统计每种语言的待翻译条数，不用 token
bun scripts/i18n/translate.js                   # 翻译全部语言
bun scripts/i18n/translate.js --lang ja,zh-HK   # 只翻译 ja，并由 zh-Hant 转换 zh-HK
bun scripts/i18n/translate.js --lang de --limit 20 --verbose
```

`--limit` 按单元计数，每个复数类别算 1 个单元。脚本不会把一个复数键截在类别中间。复制的复数类别不调用接口，不计入 `--limit`。

注意：翻译前，必须准备好 token。脚本先取环境变量 `WEBC_TOKEN`，再取 `~/.config/webc.site.yml`。不要把 token 写进仓库或日志。

脚本按下面的规则工作：

- 不翻译短标签，留给 utm-i18n skill 补译。短标签是不含占位符、最多 2 个词的文案，只数字母和数字串，例如 `Killing`、`Escape (⎋)`。撇号、连字符、斜杠会把词分开，所以 `What's New`、`CD/DVD Image` 算 3 个词，照常机翻。理由：接口拿不到上下文，短标签常选错义项，例如 Killing 译成「杀人」，Force 译成「力量」。这类错译回译后和英文相同，审校查不出来。短标签缺译时，界面显示英文。
- 发送前，把占位符换成 `{n}`。收到后还原；译文调换了参数顺序时，改成带序号的写法。
- 复数文案按目标语言的每个复数类别，用 1 个示例数字翻译 1 次。示例数字优先选英文属于 `other` 的数，例如 ru 的 one 用 21。只对应 1 个整数的类别（例如 ar 的 one）可以省略数字。
- 没有整数示例的复数类别复制另一个类别的译文：ru 和 pl 的 `other` 复制 `many`，fr、es-419、it 的 `many` 复制 `other`。复制的译文也要通过校验。
- 原来没有复数译文的键，任何 1 个类别失败时整个键都不写入，避免留下不完整的复数。
- 译文先做 5 项固定修正，然后按 `check.js` 的规则和例外清单校验，并拒绝 3 类译文：空译文、长度异常的译文、引号数量和英文不同的译文。长度例外只放行 `check.js` 的长度范围，不放行长度超过「原文 × 4 + 20」个字符的译文。引号数量只在英文含 `“”` 时检查。5 项固定修正如下：
  - 还原 `…` 和首尾空白。
  - 原文用 `“”` 时，成对的 `"` 或 `“”` 换成这种语言的引号：ja、zh-Hant、zh-HK 用「」，de 用 „“，fr 用 « »（引号内侧是不换行空格），其他语言用 “”。原文同时含直引号 `"`，或者译文已经用了 „ « 「 『 时，不换引号。
  - 删除英文中没有的不可见字符。
  - 非中日韩语言的全角标点换成半角。
  - 非中日韩语言合并连续空格，并删除每行行尾的空格。
- 不合格或接口漏返回的条目，换一个键分批重试 1 次。重试用的键每次运行都不同，所以重新运行可以拿到新的机翻结果。整批请求失败的条目不重试。
- token 无效等致命错误会立即中止整次运行。某种语言的所有批次都失败时也中止，这通常是网络或 `WEBC_API` 配置错误。
- zh-HK 不调用接口，由 zh-Hant 用 OpenCC 转换。所以先翻译 zh-Hant，再转换 zh-HK。zh-Hant 已有的短标签译文（人工或 skill 补译）照常转换。
- 每种语言完成后立即写回 catalog。中途失败时，已完成的语言不会丢失。翻译期间 catalog 被其他工具修改时，脚本停止写入，不覆盖别人的改动。

翻译只在本地运行，不在 CI 运行。翻译结果出现在 PR 的 diff 中，评审者能看到。

## 写文案的规则

- 界面文案必须写英文。不要在字符串字面量中写中文或其他语言，`check.js` 会报错。
- 同一句英文只能有 1 种译法。同一个英文词有 2 种意思时，改用显式键：

  ```swift
  String(localized: "display.noun", defaultValue: "Display", comment: "Menu title")
  ```

- 警告：改英文前先想清楚。键就是英文原文，所以只改大小写或标点也等于换了新键，全部语言的旧译文都会离开 app。旧译文记在 `i18n/removed.json` 中，包括状态和复数变体。
  - 意思不变时（例如只改大小写），把旧译文复制到新键，状态设为 `needs_review`。方法见「修改译文」。
  - 显式键的英文改动后不换键，`sync.js` 把这个键的已有译文改为 `needs_review`。
- 不要手动编辑 catalog 的格式。脚本写出的格式和 `xcstringstool` 逐字节一致。手动编辑会产生无意义的 diff。
- 格式文案（含占位符或 `%%` 的文案）中的百分号必须写成 `%%`。「50% done」这类没有占位符的文案可以直接写 `%`。
- 不要使用 substitutions（一句话里有多个复数参数）。检查脚本不支持，`check.js` 会报错。改写成每个复数只有 1 个参数的文案。
- 复数译文统一和英文的 `other` 比较。这种语言里只对应 1 个整数的类别（例如 de 的 one，ar 的 zero、one、two）可以省略数字，写成「Ein Kern」。
- 只在 iOS、visionOS 等非 macOS 平台编译的文案，macOS 构建提取不到，`sync.js` 会删除它们。fork 只发布 macOS，所以没有影响。要保留这类键，在 catalog 中把它的 `extractionState` 设为 `manual`。
- 没有字母的键（例如 `%@`）由 `sync.js` 自动标为不翻译。这个标记只加不撤：如果以后这个键有了文字，手动去掉标记。
- 系统名、产品名、格式名在界面上保持英文。这类键标为不翻译（Xcode 中是 Don't Translate），不要写译文：
  - 图标标题（`Platform/Shared/VMConfigInfoView.swift` 的 `ICON_TITLE_MAP`）由 `sync.js` 自动标记。这张表改名或移动时，`sync.js` 报错，必须同步修改 `scripts/i18n/lib/sync.js` 的 `iconTitlesOf`。
  - 其他名称在 Xcode 中手动标记，`sync.js` 保留这个标记。现在手动标记的有 Localizable 的 `RAW`、`ASIF`、`UUID`、`Mac OS`、`IPSW`、`UTM`，以及 VMDisplayWindow 的 `QvC-M9-y7g.title`（窗口标题 UTM）。
  - 有官方本地化写法时（例如 ja 的「任天堂」），保留译文，并在例外清单中写 `keep-source` 例外。标为不翻译的键的译文仍会编译进 app。
  - 句子中的名称不靠这个标记，靠 `term:<名词>` 检查。

## 修改译文

在 Xcode 中直接打开 `.xcstrings` 文件（File > Open，不用打开工程），在 String Catalog 编辑器中修改。编辑器可以把条目标为已审校（`translated`）或待审校（`needs_review`）。保存后运行 1 次 `sync.js`，让文件格式和脚本保持一致。

修改后运行 `bun scripts/i18n/check.js`。

## 检查：`check.js`

```bash
bun scripts/i18n/check.js                 # 检查全部语言
bun scripts/i18n/check.js --lang ja,ko    # 只检查 ja、ko
bun scripts/i18n/check.js --verbose       # 列出每条缺译
bun scripts/i18n/check.js --ci            # 另外检查提取结果是否已同步进 catalog
```

| 退出码 | 含义 |
|---|---|
| 0 | 没有错误，可以有警告 |
| 1 | 有错误 |
| 2 | 参数错误 |

报错的检查项：

| 规则 | 说明 |
|---|---|
| `format` | 占位符的位置或类型和英文不同；混用带序号和不带序号的写法；格式文案中的百分号没写成 `%%` |
| `empty` | 译文是空串。空串会编译进 app，界面上显示空白，而不是英文 |
| `newline` | 换行数和英文不同 |
| `edge-space` | 首尾空白和英文不同 |
| `ellipsis` | 英文是 `…`，译文写成了 `...` |
| `invisible` | 英文中没有的零宽字符、BOM、变体选择符。km、lo、th、my 允许 U+200B |
| `bidi` | Bidi 嵌入符 U+202A 至 U+202E。隔离符 U+2066 至 U+2069 只允许用于从右到左的语言 |
| `fullwidth` | 非中日韩语言出现英文中没有的全角标点，包括全角括号 |
| `cjk-leftover` | 非中日韩语言残留中日韩文字 |
| `digits` | 英文中的数字没有出现在译文中。译文可以多出数字 |
| `simplified` | zh-Hant 或 zh-HK 混入简体字。繁简通用字和异体字不算，清单在 `scripts/i18n/lib/checks.js` 的 `TRADITIONAL_OK` |
| `term:<名词>` | 专有名词被翻译、音译或改了大小写。清单在 `scripts/i18n/lib/terms.js` |
| `stale` | catalog 中还有源码已不用的键 |
| `source-cjk` | 英文原文含中日韩文字 |
| `unknown-lang` | catalog 中的语言不在 `i18n/languages.json` 中 |
| `substitutions` | 使用了 substitutions |
| `source-cjk-literal` | 源码的字符串字面量含中日韩文字。注释不检查；还没有 `git add` 的文件也检查 |
| `keep-source` | 标为不翻译的名称有译文。界面上应显示英文 |

标为不翻译的条目不算缺译，但它已有的译文仍会编译进 app，所以照样检查。英文有文字时，这类条目是名称，不能有译文（`keep-source`）。

只给警告的检查项：

| 规则 | 说明 |
|---|---|
| `plural` | 复数类别不全，运行时退回 `other`；或者英文区分复数，译文只写了 1 种形式 |
| `length` | 译文长度异常。中日韩语言是英文的 0.15 至 1.5 倍，其他语言是 0.3 至 2.5 倍。英文少于 10 个字符时不检查 |
| 缺译 | 按语言汇总条数 |

### 例外

规则误报时，在 `i18n/check-exceptions.json` 中加 1 条例外：

```json
{ "table": "VMDisplayWindow", "key": "MQ2-L1-yl7.toolTip", "rule": "term:Windows", "reason": "这里的 Windows 指窗口列表，不是操作系统" }
```

源码字面量误报时（例如语言选择列表中语言的自称），按文件和文字写例外：

```json
{ "file": "Platform/Shared/LanguagePicker.swift", "text": "简体中文", "rule": "source-cjk-literal", "reason": "语言选择列表显示语言的自称" }
```

例外的规则：

- `lang` 可以省略，省略时对所有语言生效。
- `reason` 必须写。`rule` 可以是报错规则，也可以是 `length`、`plural` 这 2 条警告。`term:<名词>` 的名词必须在专有名词清单中。审过的警告写成例外后就不再出现，避免每次检查都被同样的警告淹没。格式不对时，`check.js` 以退出码 2 退出。
- 没有命中任何问题的例外会报错，所以修好问题后必须删除对应的例外。用 `--lang` 只检查部分语言时，不报这一项，因为其他语言的例外本来就不会被用到。

## 审校与 skill

加文案、加语言、审校这 3 个流程固定在 skill `utm-i18n` 中：`.agents/skills/utm-i18n/SKILL.md`。在 Claude Code 中运行 `/utm-i18n <自然语言描述>`，例如 `/utm-i18n 审校日语新加的译文`。

审校分 4 步：

1. 改稿代理按术语表审校，输出改动和确认的条目。
2. 回译代理只看译文，把译文直译回英文。
3. 主代理比较回译和英文，意思不一致时退回改稿，最多 2 轮。
4. `review.js apply` 写回 catalog。通过审校的条目状态改为 `translated`。

`review.js` 的子命令：

| 子命令 | 用途 |
|---|---|
| `new-keys` | 列出所有语言都缺译的键，也就是新文案 |
| `export` | 导出 1 种语言的待审条目，默认是 `needs_review` |
| `apply` | 写回审校结果。逐条核对原译文并校验新译文，任何 1 条不合格时不写入 |
| `back-input` | 生成回译输入 |
| `compare-input` | 合并多种语言的英文与最新回译，作为比对代理的输入 |
| `report` | 生成审校报告（单文件 HTML） |

术语表在 `i18n/glossary/`。它复制自 VM64 官网仓库（amalthea）的 `glossary/`，去掉了官网专用的 `ui-*` 术语，这样官网和 app 使用同一种译法。

## CI

`Build` 工作流有 1 个独立的任务 check-localizations。它只依赖 macOS 引擎的构建，用空的 Windows 驱动目录构建 app，然后运行 3 步：`bun install`、`bun test`、`bun check.js --ci`。任何 1 步失败时，CI 失败。CI 不运行翻译。

这个任务不依赖 Windows 客户机工具的构建。所以 Windows 构建失败时，本地化仍能在每个 PR 上得到验证。

CI 使用最新版 Xcode。Xcode 升级后，如果 `--ci` 报 catalog「和源码不同步」，说明新版的提取或排序规则变了。在本地用同一个版本的 Xcode 重新构建，再运行 `sync.js` 并提交。
